# Faust API

Бекенд сайту нічного клубу «Faust»: меню, фото секції «Атмосфера», сесії адміна
й уся перевірка прав. Фронтенд (`../faust`) сам нічого не зберігає — він показує
те, що віддає цей застосунок.

Контракт, якому підпорядковані обидві сторони, описаний у `CLAUDE.md`:
модель даних — §5.2, публічний API — §5.3, адмінський — §5.3.1, авторизація — §5.4,
коди помилок — §9. Фронтенд уже написаний під нього, тому змінювати відповіді
можна лише разом із документом і клієнтом.

## Стек

FastAPI · SQLAlchemy 2 (async, asyncpg) · Alembic · Pydantic v2 · PostgreSQL 16 ·
PyJWT · bcrypt · Pillow + pillow-heif. Менеджер пакетів — `uv`.

## Запуск

```bash
cp .env.example .env            # заповнити DATABASE_URL, JWT_SECRET, MEDIA_BASE_URL, UPLOAD_DIR
uv sync
uv run alembic upgrade head     # схема
uv run python -m faust_api.seed # перший адмін + демо-меню
uv run uvicorn faust_api.main:app --reload --port 8000
```

Без обов'язкової змінної оточення застосунок **не стартує** — у логах буде
перелік того, чого не вистачає, а не 500 на першому запиті.

- `GET /health` — стан застосунку й БД: `200 {"status":"ok"}` або `503 {"status":"down"}`.
- `GET /docs` — схема API. У `ENVIRONMENT=production` вимкнена разом з `/openapi.json`.

Префікс усіх змістовних шляхів — `/api/v1`. Уже працюють два публічні ендпоінти
за §5.3:

- `GET /api/v1/menu` — уся барна карта: приховані категорії відфільтровані,
  обидва рівні відсортовані за `order`.
- `GET /api/v1/atmosphere` — плитки секції «Атмосфера» на головній.

Обидва викликає **сервер Next**, а не браузер, тож CORS не налаштований і не
потрібен.

Ще три ендпоінти обслуговують сесію адміністратора за §5.4:

- `POST /api/v1/auth/login` — `{ email, password }` → `{ access_token, expires_in, user }`.
  П'ять невдалих спроб за десять хвилин з однієї адреси, і шоста чекає, навіть
  якщо пароль правильний.
- `GET /api/v1/auth/me` — Bearer → `{ user }` або `401`. Цим фронтенд перевіряє,
  чи сесія ще жива: сам він токен не відкриває.
- `POST /api/v1/auth/logout` — піднімає `token_version`, тобто вимикає всі
  видані токени одразу, на всіх пристроях.

Токен живе 7 днів. Коли до кінця лишається менше доби, відповідь під сесією
несе заголовки `X-Session-Token` і `X-Session-Expires-In` — фронтенд тихо
перезаписує кукі, і власника не викидає на форму входу без пояснень.

Адмінські ендпоінти за §5.3.1 — під `/api/v1/admin`, усі під Bearer-токеном:
категорії, позиції та плитки «Атмосфери», з CRUD, сортуванням `↑↓` і
завантаженням фото.

Фото роздаються самим API:

- `GET /media/<ключ>-<варіант>.webp` — `thumb` 320, `card` 640, `full` 1280,
  квадрат 1:1, `Cache-Control: public, max-age=31536000, immutable`.
- Абсолютна адреса складається з `MEDIA_BASE_URL`. Локально це
  `http://localhost:8000/media`; у проді — `https://media.faust.bar`, і тоді
  зворотний проксі має відображати `media.faust.bar/<ключ>` на `/media/<ключ>`
  цього застосунку — це вже робить `Caddyfile` у корені репозиторію.
- Ім'я файлу генерує сервер: id рядка-власника плюс хеш вмісту. Тому файл
  ніколи не перезаписується (звідси `immutable`), а дві позиції з однаковим
  кадром мають власні копії — видалення однієї не гасить фото іншої.
- Формат визначається за **magic bytes**, а не за розширенням чи MIME:
  `jpeg`, `png`, `webp`, `heic`/`heif`. Ліміт — 5 МБ. Кадр повертається за
  EXIF, метадані (EXIF, ICC, XMP, GPS) не потрапляють на диск.

## Схема бази

```bash
uv run alembic upgrade head        # накотити
uv run alembic downgrade base      # відкотити повністю
uv run alembic revision --autogenerate -m "опис"   # нова міграція після правки моделей
```

Модель описана в `src/faust_api/models/` і повторює §5.2 дослівно. Схема
береться **з міграцій**, не з `create_all()`: тест `tests/db/test_migrations.py`
падає, щойно моделі й міграції розійшлися, — щоб це помітив розробник, а не
деплой.

## Сід

```bash
uv run python -m faust_api.seed
```

Робить дві речі. Гарантує адміністратора з `SEED_ADMIN_EMAIL` і
`SEED_ADMIN_PASSWORD` (пароль хешується bcrypt-ом і в базу як текст не
потрапляє). І, **лише якщо база порожня**, наливає демо-меню: 4 категорії з
однією прихованою, 7 позицій (з фото, без фото, одна «немає», мітки `hit` і
`new`) і 3 плитки атмосфери з однією прихованою. Повторний запуск нічого не
дублює й не перезаписує — правки власника переживають повторний деплой.

> Фото для сіду **малюються** під час запуску — темний градієнт у палітрі сайту,
> який видно, що він заглушка. Справжні кадри належать власнику й приїжджають
> через адмінку, а в репозиторії бінарників немає. Файли лягають у `UPLOAD_DIR`
> тим самим шляхом, що й завантажені: три WebP-варіанти на кожен знімок.

## Пароль адміністратора

```bash
uv run python -m faust_api.set_admin_password owner@faust.bar
# у контейнерах:
docker compose run --rm api python -m faust_api.set_admin_password owner@faust.bar
```

Пароль питається у приглашенні, а не передається аргументом — інакше він
осів би в історії оболонки й у `docker ps`. Мінімум 8 символів, як і у формі
входу. Разом зі зміною піднімається `token_version`, тобто **всі видані токени
вмирають одразу, на всіх пристроях** (§5.4). Ендпоінта для цього немає й не
буде: пароль міняє той, хто має доступ до сервера, а не веб-форма.

Сід пароль наявного адміністратора не чіпає — він лише додає рядок, якщо його
ще немає.

## Контейнер і деплой

Образ описаний у `Dockerfile`: дві стадії, `python:3.13-slim`, non-root
(`faust`, uid 1001), залежності ставить `uv sync --frozen`. У фінальний образ
не потрапляють ні `uv`, ні лок-файл, ні тести. Кількість воркерів uvicorn
береться зі змінної `API_WORKERS`.

> **Один воркер за замовчуванням — навмисно.** Ліміт спроб входу рахується в
> памʼяті процесу, тож N воркерів означають N відер і до 5×N здогадок за десять
> хвилин. Піднімати варто разом із перенесенням лічильника з памʼяті процесу.

Уся композиція — у `docker-compose.yml` кореня репозиторію: `postgres`, `api`,
`web` (Next), `proxy` (Caddy). Запуск на чистій машині:

```bash
cp .env.example .env                                  # у корені репозиторію
docker compose up -d postgres api                     # схема накотиться сама
docker compose run --rm api python -m faust_api.seed  # перший адміністратор
docker compose up -d --build                          # решта сайту
```

Чому три команди, а не одна:

- **Міграції** — окремий сервіс `migrate`, який виконує `alembic upgrade head`
  і завершується; `api` стартує лише після його успіху. Застосунок сам схему
  не чіпає, тож код ніколи не обслуговує базу на міграцію позаду.
- **Сід** — окрема команда, бо демо-меню не має зʼявлятись на живому сайті
  тільки тому, що хтось перезапустив стек.
- **`web` збирається останнім**, бо вітрина в ньому пререндериться. Образ,
  зібраний проти непіднятого API, несе порожнє меню, і полагодити його
  ревалідацією вже не вийде: сторінка, яка жодного разу не отримала даних, не
  має ні тега кешу, ні таймера. Адресу для збірки задає `BUILD_MENU_API_URL`.

Порт `8000` публікується **тільки на loopback**: назовні API не виходить —
браузер спілкується з ним через Next, а фото роздає проксі за іменем
`media.faust.bar`. Перезапуск API сайт не кладе: публічні сторінки статичні.

## Бекап

Дві речі, і обидві обовʼязкові: **база** і **том з фото**. База без тому — це
меню з битими картинками; том без бази — купа файлів, про які ніхто не знає.

```bash
# /usr/local/bin/faust-backup.sh
set -eu
DEST=/var/backups/faust
STAMP=$(date +%F)
mkdir -p "$DEST"

docker compose -f /opt/faust/docker-compose.yml exec -T postgres \
  pg_dump -U faust -Fc faust > "$DEST/db-$STAMP.dump"

docker run --rm -v faust_uploads:/data:ro -v "$DEST":/backup alpine \
  tar czf "/backup/uploads-$STAMP.tar.gz" -C /data .

find "$DEST" -type f -mtime +30 -delete
```

```cron
# щоночі о 05:00, коли клуб уже зачинений
0 5 * * * /usr/local/bin/faust-backup.sh >> /var/log/faust-backup.log 2>&1
```

Відновлення:

```bash
docker compose exec -T postgres pg_restore -U faust -d faust --clean < db-2026-08-19.dump
docker run --rm -v faust_uploads:/data -v "$PWD":/backup alpine \
  tar xzf /backup/uploads-2026-08-19.tar.gz -C /data
```

Копію треба забирати з машини. Бекап, який лежить на тому ж диску, що й
оригінал, рятує від помилки й не рятує від втрати диска.

## Перевірки

```bash
uv run ruff check .      # лінт
uv run ruff format .     # форматування
uv run mypy              # типи, strict
uv run pytest            # тести
```

Усі чотири мусять бути зелені перед тим, як крок вважається завершеним.

Тестам із `tests/db/` потрібен живий Postgres — `RESTRICT` і унікальний індекс
це обіцянки бази, а не коду. Адреса береться з `TEST_DATABASE_URL` (за
замовчуванням `postgresql+asyncpg://faust:faust@localhost:5432/faust_test`).
Немає сервера — ці тести **пропускаються з поясненням**, решта йде як завжди:

```bash
docker run -d --name faust-pg -e POSTGRES_USER=faust -e POSTGRES_PASSWORD=faust \
  -e POSTGRES_DB=faust -p 5432:5432 postgres:16-alpine
docker exec faust-pg psql -U faust -c "CREATE DATABASE faust_test"
```

## Що де лежить

| Тека | Що в ній |
|------|----------|
| `src/faust_api/settings.py` | усі змінні оточення, єдине джерело |
| `src/faust_api/errors.py` | ієрархія помилок §9 — тут вона породжується |
| `src/faust_api/handlers.py` | будь-який збій → `{ error: { code, message, fields? } }` |
| `src/faust_api/db.py` | engine, сесія на запит, проба здоров'я |
| `src/faust_api/models/` | чотири сутності §5.2 |
| `src/faust_api/security/` | паролі, підпис токенів, перетворення Bearer на адміна |
| `src/faust_api/seed.py` | перший адмін і демо-меню |
| `src/faust_api/routers/` | ендпоінти: `health`, публічні `menu`/`atmosphere`, `auth`, `media`; `admin/` — категорії, позиції, атмосфера |
| `src/faust_api/schemas/` | Pydantic-моделі відповідей — це і є контракт §5.3 |
| `src/faust_api/services/` | те, чого не має знати роутер: обробка й зберігання фото, порядок `↑↓`, вебхук ревалідації, ліміт спроб входу |
| `migrations/` | Alembic |
| `tests/unit/` | логіка: налаштування, помилки, паролі, токени, ліміт спроб |
| `tests/contract/` | форма відповідей — те, на що спирається фронтенд |
| `tests/photos.py` | кадри для тестів завантаження: малюються, а не лежать бінарниками |
| `tests/db/` | обіцянки схеми: `RESTRICT`, унікальні індекси, міграції, сід |

## Дані і файли

- Фото зберігаються в теці з `UPLOAD_DIR` і роздаються з `/media/<ключ>`.
  У проді це том Docker: **втрата тому = втрата всіх фото меню й атмосфери.**
  Оригінали не зберігаються — лише три WebP-варіанти.
- Пароль адміна не існує ні в коді, ні в сіді — лише в `SEED_ADMIN_PASSWORD`
  під час першого запуску сіду. У базі — тільки bcrypt-хеш, cost 12.
- `JWT_SECRET` живе тільки тут. Фронтенд токен не перевіряє: для нього він непрозорий.
